## Decision

**Spring Boot auto-initialization** (`spring.sql.init.mode=always` with the `mysql` profile).
No manual SQL runs, no init-container migration job.

| Option | Verdict | Why |
|--------|---------|-----|
| Spring auto-init (`mysql` profile) | **Chosen** | Scripts already ship in each service jar (`classpath*:db/mysql/*.sql`) and are idempotent (`CREATE TABLE IF NOT EXISTS`, `INSERT IGNORE`). Zero extra moving parts. |
| Manual `mysql` client run | Rejected | Not repeatable; drifts from the app version. |
| Init container / Job (Flyway, Liquibase) | Deferred | Right answer for real production schema migrations, but the upstream app has no migration tooling and the app repo is read-only. |

## One shared database

All three domain services use **one** database, `petclinic`, on the single RDS instance
(`petclinic-{env}-mysql`). It is created by Terraform (`db_name = "petclinic"` in the RDS module);
each `schema.sql` also starts with `CREATE DATABASE IF NOT EXISTS petclinic; USE petclinic;`.

Separate databases are not possible: `visits.pet_id` has a foreign key to `pets.id`, which is
owned by customers-service.

## Schema scripts (app repo, read-only)

| Order | Service | Script | Tables |
|-------|---------|--------|--------|
| 1 | customers-service | `spring-petclinic-customers-service/src/main/resources/db/mysql/schema.sql` + `data.sql` | `types`, `owners`, `pets` |
| 2 | vets-service | `spring-petclinic-vets-service/src/main/resources/db/mysql/schema.sql` + `data.sql` | `vets`, `specialties`, `vet_specialties` |
| 3 | visits-service | `spring-petclinic-visits-service/src/main/resources/db/mysql/schema.sql` + `data.sql` | `visits` (FK → `pets`) |

7 tables total.

### Ordering

visits-service **must not** start its schema init before `pets` exists, otherwise the
`FOREIGN KEY (pet_id) REFERENCES pets(id)` fails and the pod crash-loops. Enforcement:

1. Deploy customers-service before visits-service (ArgoCD sync waves when Helm/ArgoCD lands).
2. visits-service gets an init container that waits for customers-service readiness
   (`/actuator/health/readiness`). Even without it, Kubernetes restarts converge once
   customers-service has created `pets`, because the scripts are idempotent.

vets-service is independent and can start in any order.

## Connection settings for K8s ConfigMaps / Helm values

| Variable | Source | Value |
|----------|--------|-------|
| `SPRING_PROFILES_ACTIVE` | Helm values | `docker,mysql` |
| `SPRING_DATASOURCE_URL` | Helm values (from `terraform output -raw rds_jdbc_url`) | `jdbc:mysql://{rds-endpoint}:3306/petclinic` |
| `SPRING_DATASOURCE_USERNAME` | K8s Secret `rds-credentials` key `username` (ExternalSecret, PETPLAT-35) | `petclinic` |
| `SPRING_DATASOURCE_PASSWORD` | K8s Secret `rds-credentials` key `password` (ExternalSecret, PETPLAT-35) | from `petclinic/{env}/rds-credentials` |

Example: `jdbc:mysql://petclinic-dev-mysql.abc123.ap-south-1.rds.amazonaws.com:3306/petclinic`

> **TLS is required.** The parameter group sets `require_secure_transport=1`. MySQL Connector/J
> defaults to `sslMode=PREFERRED`, so the URL above negotiates TLS automatically. **Do not**
> append `useSSL=false` (the upstream config repo's local-dev URL does); setting
> `SPRING_DATASOURCE_URL` explicitly overrides it.

## Credentials

- Generated by Terraform (ephemeral `random_password`, 24 chars, special characters).
- Stored only in Secrets Manager `petclinic/{env}/rds-credentials` as
  `{"username":"petclinic","password":"..."}`. Terraform passes the password through
  write-only arguments, so it is **not** in state or plan files.
- Rotate: increment `master_password_version` on the `rds` module, then plan and apply. The
  new password is written to RDS and the secret in the same apply. ESO picks it up within
  `refreshInterval` (1h); restart the DB-backed deployments afterwards.
- **Recovery after a failed apply:** the password is regenerated on every run and written
  only when `master_password_version` changes. If an apply fails after the secret was
  written but before the DB was created, the next apply can leave RDS and the secret with
  different passwords. Bump `master_password_version`, apply again, then run the login
  check in [Verification](#verification-petplat-26) step 3.

## Verification (PETPLAT-26)

```bash
cd terraform/environments/dev
ENDPOINT=$(terraform output -raw rds_endpoint)

# 1. Instance is available
aws rds describe-db-instances --db-instance-identifier petclinic-dev-mysql \
  --region ap-south-1 --query 'DBInstances[0].DBInstanceStatus' --output text   # => available

# 2. Secret exists with username/password keys (prints keys only, not values)
aws secretsmanager get-secret-value --secret-id petclinic/dev/rds-credentials \
  --region ap-south-1 --query SecretString --output text | jq 'keys'           # => ["password","username"]

# 3. Connectivity from an EKS pod (pods carry the node SG, which the RDS SG allows on 3306)
PASS=$(aws secretsmanager get-secret-value --secret-id petclinic/dev/rds-credentials \
  --region ap-south-1 --query SecretString --output text | jq -r .password)
kubectl run mysql-debug -n petclinic-dev --rm -it --restart=Never --image=mysql:8.4 \
  --env="MYSQL_PWD=$PASS" -- \
  mysql -h "$ENDPOINT" -u petclinic --ssl-mode=REQUIRED -e "SELECT VERSION(); SHOW DATABASES;"

# 4. After customers/vets/visits are deployed: 7 tables exist
kubectl run mysql-debug -n petclinic-dev --rm -it --restart=Never --image=mysql:8.4 \
  --env="MYSQL_PWD=$PASS" -- \
  mysql -h "$ENDPOINT" -u petclinic --ssl-mode=REQUIRED petclinic -e "SHOW TABLES;"
```

Expected tables: `owners`, `pets`, `specialties`, `types`, `vet_specialties`, `vets`, `visits`.
